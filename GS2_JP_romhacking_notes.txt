  GYAKUTEN SAIBAN 2 (GBA, JAPAN) - ROMHACKING NOTES
  Addresses, data formats and a script reference for the original Japanese ROM
================================================================================

  For anyone who wants to hack 逆転裁判2 on the Game Boy Advance: translators,
  people fixing or changing cases, people writing tools.  Everything here is
  about the clean Japanese ROM (section 1) and was checked against it.

  Most names in CamelCase (gScriptContext, PutCharInTextbox, ...) are the names
  used by the pwaa2 decompilation, so you can look them up in its source:
      https://github.com/atasro2/pwaa2
  It builds a byte-for-byte copy of this ROM.  If you are going to do anything
  big (new features, a variable-width font, moving tables), use it: you can
  change C code and rebuild instead of patching assembly by hand.  These notes
  are the "where is it and how does it work" summary of that work plus what we
  learned hacking the game.

  This file is UTF-8 (it contains Japanese).  Best read with a monospaced font.
  Written October 2026.

How to read these notes
-----------------------
* Addresses are GBA addresses.  The ROM is mapped at 0x08000000, so
      file offset = address - 0x08000000      (0x08022BFC is at offset 0x22BFC)
* EWRAM is 0x02000000-0x0203FFFF, IWRAM 0x03000000-0x03007FFF.
* u8/u16/u32 are unsigned 8/16/32-bit numbers, s16 a signed one.  Everything is
  little-endian (the low byte comes first in the file).
* The game's code is Thumb.  A pointer to a function has bit 0 set: the table
  entry 0x08007D95 means "Thumb code at 0x08007D94".  Addresses of functions in
  these notes are the real (even) start addresses.
* Script codes are written in brackets with hex numbers: [0E 0x300] is control
  code 0x0E with one argument 0x0300.  Sections are numbered in hex too.
* "LZ77" means the GBA BIOS compression (type 0x10, the format of the BIOS calls
  LZ77UnCompWram/LZ77UnCompVram).  Any GBA LZ77 tool can pack and unpack it.
  The game unpacks with the BIOS calls, so data you pack must not use the
  "VRAM-unsafe" back-reference distance of 1 when it is unpacked to VRAM (most
  tools have a VRAM-safe option; the script and backgrounds go to EWRAM).
* Episode / part numbers: "Ep2" is episode 2.  Each episode is split into script
  "parts"; the game counts all parts with one number, scenarioIdx (0-21).

1. The ROM
================================================================================

Header title ......... GYAKUTEN_SA2
Game code ............ A3GJ   (A3G = the game, J = Japan)
Maker code ........... 08     (Capcom)
Version .............. 0
Size ................. 8 MiB (0x800000 bytes)
Save type ............ SRAM 32 KiB (the ROM contains the string SRAM_V112)
CRC32 ................ 191AD26A
MD5 .................. 41ae841d5771e442f7fb5393906cb898
SHA-1 ................ f7a156dbed52d3edb8104112ae40e6e2aaca57f9

If your dump does not match, it is a different version or already patched,
and the addresses below will not fit.

Useful tools: an emulator with a debugger (mGBA, no$gba), a hex editor, a GBA
LZ77 packer/unpacker, a graphics tool that knows GBA 4bpp/8bpp tiles (for
example Tile Molester or the gbagfx tool that comes with the decompilation),
and a script-aware dumper (the control codes have arguments, see section 5, so
a plain table file is not enough to dump the script cleanly).


================================================================================
2. Map of the ROM
================================================================================

0x08000000-0x0801AD87  program code (Thumb), main loop, script engine, everything
0x0801AD88-0x0802434F  game data tables (backgrounds, cases, evidence, persons, ...)
0x08024350-0x08111D17  sound engine tables, then all music and sound data
                       (song table gSongTable at 0x0802E584)
0x08111E18-0x08112A6B  pointer tables (processes, script commands, per-part
                       tables, name tag map)
0x08112A6C-0x0812FFFF  unused, filled with 0xFF (about 117 KB)
0x08130000-0x08730AEB  graphics (backgrounds, people, font, evidence, menus)
0x08730AEC-0x087FC547  the script: std_scripts, then the 22 compressed parts
0x087FC548-0x087FFFFF  unused, filled with 0xFF (about 15 KB)

The ROM is full.  The GBA can address up to 32 MiB of cartridge ROM and the game
never checks its size, so the easiest way to get room is to expand the ROM to
16 MiB (append 8 MiB of 0xFF) and put new or bigger data at 0x08800000 and up,
then repoint the table entry that points to it.  (The header checksum at 0xBD
only covers the header, it does not change when you expand.)


================================================================================
3. Episodes and script parts
================================================================================

The game's script is split into 22 parts, one per "chapter" of an episode.
gMain.scenarioIdx (RAM 0x03003863) says which part is loaded.

  gScriptTable           0x08022BFC  22 pointers (u32), one per part, to the
                                     LZ77-packed script of that part
  gCaseStartProcess      0x0801C3D8  22 bytes: 3 = the part starts in the
                                     court process, 4 = in the investigation process
  gCaseGameoverSections  0x0801C3EE  u16 per part: the section the game goes
                                     to when the health bar runs out (0 = none)
  std_scripts            0x08730AEC  the shared sections 0x00-0x23 (not packed)

When a part starts, its script is unpacked to RAM at 0x02011FC0 (gScriptHeap) and
section 0x80 runs.  Code [16] at the end of a part adds 1 to scenarioIdx and goes
to the save prompt; when the new part is the first of a new episode, the
"new episode unlocked" screen comes first (CourtExit, 0x0800D838).

where the packed script is, its packed and unpacked size, how many sections and

part's script in script/scenario_E_P_script.phscr (E = episode - 1, P = part

================================================================================
4. The script format
================================================================================

4.1  Parts and sections
-----------------------
A part, once unpacked, looks like this (all offsets are in bytes from the start
of the part):

    +0      u32  N         number of entries in the table
    +4      u32  table[N]  first the sections, then the jump labels (below)
    ...     the sections, one after the other, as u16 codes

The sections come first in the table, in order: table[0] is the byte offset of
section 0x80, table[1] of section 0x81, and so on.  Section number = 0x80 + its
index in the table.  Their offsets always increase.

Some parts have "jump labels" after the sections (91 in the whole game).  A
label is not an offset; it is two u16s packed in the u32:
    low half  = byte offset inside the target section
    high half = target section - 0x80
The long jumps [35]/[36] use them (section 5).  You can tell where the labels
start because the values stop increasing / point past the end of the part.

Sections 0x00-0x23 are not in the parts: they are std_scripts at 0x08730AEC,
the same format (a u32 count of 36, then 36 offsets, then the codes), not packed,
always available.  They hold the save/erase questions, the title cards, the
"nothing here" line and the generic wrong-evidence penalties (appendix G).

4.2  Codes
----------
A section is a stream of u16 values:
    0x0000-0x007F  control code.  Each one has a fixed number of u16 arguments
                   that follow it (section 5).
    0x0080 and up  a letter: glyph number = value - 0x80 (font, section 6 and
                   appendix A).  0x0080 is '０', 0x0180 is 'ー', 0x017F is a space.

There is no end-of-string marker.  A section ends with [0D] (go to the next
section), and the engine reads straight on into the next section, whose [00]
starts it fresh.  So a section with no [0D] just "falls through" into the next.

The "next section" starts as current + 1 at every [00]; [20], [2C], [0A], a
choice ([08]/[09]), [2A] and the game itself (Talk, Present, Examine...) change it.

4.3  Read flags and fast-forward
--------------------------------
Every time a section ends, its bit in gMain.sectionReadFlags (RAM 0x030038B0,
256 bits for sections 0x80-0x17F, not range-checked, see section 18) is set.
In investigations, A or B fast-forwards a section that has already been read
(the text appears at once, boxes go on by themselves while B is held); the code
only starts this skip in the investigation process, never in court.  The read
flags are cleared when a trial part starts and when it ends; once an episode
has been cleared, they are all set at the start of its parts
(SetCurrentEpisodeBit, 0x0800D450).

4.4  How big can a part be?
---------------------------
The part is unpacked at 0x02011FC0.  The game unpacks other things right after
it: from 0x0202CFC0 the big backgrounds (480 wide, 240x320...; scrolling reads
them there too), the title screen and the episode-select graphics, and from
0x02036500 the normal 240x160 backgrounds.  So:
  * a part of up to 0x1B000 bytes (110,592) is always safe;
  * a bigger part (up to 0x24540 bytes, 148,800) loses its end whenever a big
    background is shown, and must be reloaded before that end is used again.
Five parts are bigger than 0x1B000 (scenarioIdx 8, 11, 15, 19 and 21; the
biggest is 142,200 bytes).  The script reloads the part with [67] in four
places (two of them right after a big background), and the room setup code of
five investigation segments calls LoadCurrentScriptIntoRam
(0x080074A4) in some rooms.  If you make a part bigger than
0x1B000 bytes, check what follows every big background, or move the buffer
(in the decompilation).

4.5  Editing the script safely
------------------------------
* Changing the length of a section moves every section after it.  Rebuild the
  offset table (and keep the jump labels pointing at the same codes).
* A short jump [35 x offset] (bit 0x80 clear) holds a byte offset inside its own
  section: if you add or remove text before the jump target, fix the offset.
* A long jump label (above) holds a byte offset inside its target section: same.
* Repack with LZ77.  If it is bigger than before, put it in free space (or in an
  expanded ROM) and change the part's pointer in gScriptTable
  (0x08022BFC + 4 * scenarioIdx).  Nothing else points into the packed data.
* The game keeps no other copy of the text: once the part is unpacked, every
  script position is "heap + offset".  A save file stores the script position
  as a RAM pointer (gScriptContext.scriptPtr) - saves made in a section whose
  position you changed may resume at the wrong place.  Start a new game to test.
* Keep the number of glyphs per line in mind (16, section 6).

4.6  Dumping a part, step by step
---------------------------------
 1. Read the u32 at gScriptTable + 4 * scenarioIdx (0x08022BFC); subtract
    0x08000000 to get the file offset of the packed part.
 2. Unpack it (LZ77 type 0x10: a 4-byte header 0x10 + 24-bit unpacked size,
    then the data).
 3. Read N = the first u32, then the N u32 table entries.  Walk the entries while
    they increase and stay inside the part: those are the sections.  Section
    0x80 + i starts at table[i] and ends where table[i+1] starts (the last one
    at the end of the part).  The remaining entries are jump labels.
 4. Read each section as u16 values.  A value below 0x80 is a control code:
    print it with the number of arguments section 5 gives it and skip them.  A
    value of 0x80 or more is glyph value - 0x80 (appendix A).
 5. To put it back: write the sections, rebuild the table with the new offsets
    (labels too), pack, and store the part (section 4.5).
The shared sections (std_scripts) are the same without steps 1-2.


================================================================================
5. Control codes
================================================================================

Every control code, with the number of arguments the engine reads after it.
The handler of code n is gScriptCmdFuncs[n] (table at 0x08112124, 0x72
pointers).  "Never used" means the Japanese script never uses it.

A handler returns 0 (run the next code in the same frame), 1 (stop for this
frame; the same code is run again next frame if the pointer was not moved) or
2 (like 0, and turn off text skipping).

Args are shown by name; "a<<8|b" means one u16 holding a in the high byte and b
in the low byte.

[00]  0 args                                    handler 0x08007D94  used   2996
      Section start. Resets the text state: empties the box, text position back
      to the first line, speed 3, colour white, text origin (9,116), next
      section = this one + 1, map markers off. Every section begins with it.

[01]  0 args                                    handler 0x08007DAC  used  17424
      Line break.

[02]  0 args                                    handler 0x08007DDC  used  18553
      Wait for A (the arrow blinks in the box), then clear the box. While it
      waits the speaker is set to the idle pose; after the press, to the talking
      pose, then a 10-frame pause. The usual 'end of a text box'.

[03]  1 arg: colour                             handler 0x08008108  used   7967
      Text colour: 0 white, 1 orange-red (key words), 2 blue (thoughts), 3
      green.

Notes on the codes
------------------
* Fades: [12 0x204 1 0x1F] fades to black (4 frames per step); [12 0x104 1 0x1F]
  fades back in.  Wait with [0C] while it runs; the script does not wait.
* Choices look like this in the script:
      ...question text [07] option one [01] option two [08 sec1 sec2]
  [09] works the same with three lines.
* Courtroom pans [1A pan dir person pose], then the script sets the background:
      [1A 0 0x1000 ..]  defense -> witness       [1A 0 1 ..]  witness -> defense
      [1A 1 0x1000 ..]  prosecution -> defense   [1A 1 1 ..]  defense -> prosecution
      [1A 2 0x1000 ..]  prosecution -> witness   [1A 2 1 ..]  witness -> prosecution
* Typical person line:  [1E 0x7 0x104 0x0][1B 0x7][0E 0x700] text...
  = show the Judge (person 7) with talking pose 0x104 and idle pose 0, show his
  bench (background 7), name tag "サイバンチョ" (speaker 7).
* [0C n] counts frames (60 a second).  [0C 0] never ends - do not use it.
* [3C] and [4B] do not check that the map marker exists: on a marker that is not
  shown they write to gMapMarker[0xFF], out of the array.  Show it first.
* Argument counts matter: a tool that gets one wrong reads every code after it
  wrongly.  The counts here tokenise all 2,995 sections of the game exactly.


================================================================================
6. Text, font and name tags
================================================================================

6.1  The font
-------------
gCharSet (0x081AE3A8): 1536 glyph slots of 128 bytes.  Each glyph is 16x16
pixels, 4bpp, stored as four 8x8 tiles in the order top-left, top-right,
bottom-left, bottom-right.  Pixel values 1-3 are the three shades of the
letter, 0 is transparent.
  0x000-0x587  the 1,416 real glyphs (table in appendix A)
  0x588-0x58F  empty
  0x590-0x5FF  a leftover copy of 0x490-0x4FF
Glyph 0xFF is the full-width space (the engine plays no blip for it).  Glyphs
0x100 'ー' and 0x151 '一' look almost the same: 0x100 is the long-vowel mark
(カ'ー'ド), 0x151 the kanji one.  0x0F4 is a short dash, 0x481 another '一' (both
unused).  The space 0x588-0x5FF can take 120 new glyphs.

gTextPal (0x081AE388) is the text palette, loaded as OBJ palette 0:
    colours 1-3   white letter          ([03 0])
    colours 4-6   orange-red letter     ([03 1], key words)
    colours 7-9   blue letter           ([03 2], Phoenix's thoughts)
    colours 10-12 green letter          ([03 3])
The colour code works by adding 3 * colour to every pixel of the glyph.

6.2  How text is drawn
----------------------
Every letter is its own 16x16 sprite.  PutCharInTextbox (0x080077F4)
copies the glyph into OBJ VRAM and fills an entry of gTextBoxCharacters
(0x03003E70, 63 entries of 12 bytes: state (0x8000 = shown | glyph),
attr2, x, y, colour).  DrawTextAndMapMarkers (0x080079A4) turns the
entries into OAM every frame.

  * The box has 2 lines of 16 letters (entries 0-31), a third line with [6E 1]
    (entries 32-47).  There is no automatic wrapping: lines are broken by [01].
  * Letters are 14 px apart, lines 18 px apart, from the text origin
    (gScriptContext.textXOffset/textYOffset = 9, 116).  [48] moves the origin.
  * Line r, column c uses OBJ tiles 64*r + 4*c (tiles 0-127 hold the box text).
  * Choices: the options are drawn in "fullscreen" mode as entries 32-62, OBJ
    tiles 128 + 4*n, rows 20 px apart from (24, 70).  All options together can
    have at most 31 letters.  The cursor is glyph 226 ('☞') copied to tile 252.
  * The "next" arrow is two BG1 map cells (622/623 = row 19, columns 14-15) that
    [02] animates (gTextboxDownArrowTileIndexes, 0x08022C98).

For a translation the fixed 14 px grid and the 16-letter lines are the main
limits.  Variable-width text needs new code: the usual approach hooks the two
calls of PutCharInTextbox and DrawTextAndMapMarkers (or rewrites them in the
decompilation).  Remember the third line ([6E]) and the choice screens.

6.3  Name tags and voice blips
------------------------------
[0E spk<<8|side] shows a name tag.  The name tags are pictures, not text:
    gSpeakerToNametagMap 0x08111ED0  56 bytes: speaker id -> picture (0 = no tag)
    gGfxNameTags         0x0813891C  the pictures, 48x16 px, 4bpp.  Picture n
                         is at +(n / 5) * 0x800 + (n % 5) * 0xC0: 6 tiles for the
                         top row, the bottom row 0x400 bytes further.
    gNameTagTiles        0x0801B1C0  the BG1 map cells used for a tag
    SetTextboxNametag    0x08004000
The voice blip comes from gSoundCueTable (0x08022C54, 56 bytes, by
speaker id): 0 = male blip (sound 45), 1 = female (sound 46).  [30 2] switches
to the typewriter click (sound 68) used for dates and places.
Speaker ids and their tags are in appendix B.

6.4  The text box
-----------------
The box is drawn on BG1 from the 32x16 map template gTextboxTiles
(0x0801B1D8).  The box rows are BG1 map rows 12-19 (the name tag is in rows
12-13).  SetTextboxSize, UpdateTextbox, SlideTextbox and
CopyTextboxTilesToBG1MapBuffer handle it; [1C] shows, hides and slides it.

6.5  Other text that is not in the script
------------------------------------------
These are all pictures - a translation has to redraw them:
  * name tags (above)
  * location names for Move: gGfxLocationChoices (0x081DE3E8), one
    128x32 4bpp picture (0x800 bytes) per room id (appendix F)
  * talk topics: gGfxTalkChoices (0x081EB3E8), same size, 141 pictures,
    picked by gTalkData.iconId
  * evidence/profile names and descriptions: one LZ77-packed picture each
    (section 12)
  * text baked into backgrounds: newspaper pages, floor plans, notes, title
    cards (appendix D, the "text card" / "floor plan" entries)
  * menus, buttons, the testimony / cross-examination logos, "Guilty" /
    "Not Guilty", the title screen: graphics in the 0x08130000 area (appendix I)

================================================================================
8. Flags
================================================================================

There are three sets of flags, picked by the "flag set" number in [10]:
    set 0  script flags     gMain.scriptFlags    0x0300386C  256 flags (8 u32s)
    set 1  game state       gMain.gameStateFlags 0x0300388C  32 flags
    set 2  talk-end flags   gMain.talkEndFlags   0x03003890  256 flags
Flag n is bit (n % 32) of u32 number (n / 32).  ChangeFlag(set, n, on) is at
0x080042FC, GetFlag(set, n) at 0x08004338 (table gFlagPtrs 0x08111F08).

The script flags are the case's memory: what was examined, which talk topics
were heard, which events happened.  [10] sets/clears any flag, [2A] and [35]
test script flags, and the investigation room code (section 10) tests them to
decide who is in a room and what happens when you enter.  They are all cleared
when a part starts (also when it follows the previous part), so each part sets
up what it needs; carry nothing over in flags from one part to the next.

Game-state bits seen in the code: 0x1 a shake is running, 0x10 player locked
out ([26 1]: no skip, no R, no START), 0x100 / 0x200 present mode set by
[11] / [21].

Episode progress is gMain.caseEnabledFlags (0x03003864): bits 0-3 = episodes 1-4
can be chosen, bits 4-7 = episodes 1-4 cleared (cleared episodes count all text
as read).  Code [49] at the very end of the game sets bit 7 and saves.

9.1  Testimony and cross-examination
------------------------------------
A testimony is a run of sections, one per statement; each statement ends with
[15] (halt).  While halted in the cross-examination the court process reads the
keys: A or Right = next statement (gScriptContext.nextSection), B or Left =
previous one (current - 1), L = "Hold it!" if [0F] gave this statement a press
section.  [6F] names the section after the last statement (Right does not go
there, only A), [28]/[29] start and stop the testimony / cross-examination
modes.

9.2  Presenting in court
------------------------
gCourtPresentData (0x08111F6C) has one pointer per part to a list of
8-byte entries:
    +0 u16  section the player is in when presenting (the statement)
    +2 u16  evidence or profile id
    +4 u16  section to go to
    +6 u8   script flag the entry needs (0xFF = always)
    +7 u8   0 = Phoenix slams the desk, anything else = no desk slam
    a 0xFFFF section ends the list
GetQuestioningPresentedSection (0x080131F0) looks it up.  No
match = a wrong answer: when the script itself asked for evidence ([11]/[21]),
the game goes on to the section after the current one (the case's own "that's
wrong" scene); during a cross-examination it picks one of the generic penalty
sections 0x1F-0x22 (appendix G) at random.

9.3  Health
-----------
The health bar runs 0-80 (gMain.hpBarValue, 0x03003848, s16).  [54 2 n] sets
the damage, [54 0 3] takes it (with the animation), [54 0 1]/[54 0 2] slide the
bar in/out; [43] shows/hides it.  When it reaches 0 the game goes to the part's
game-over section (gCaseGameoverSections).  [0A section] is the end of a box
that only jumps if the player still has health.  Health is set back to 80 when
an investigation segment starts.

9.4  The Court Record at the start of a part
--------------------------------------------
gCourtRecordInitialItemLists (0x08111F14): one pointer per
part to a byte list: profile ids until 0xFE, then evidence ids until 0xFF.  It
replaces the whole record at the start of every part, also when the part follows
the previous one (InitializeCourtRecordForScenario,
0x08011688).  So evidence a part adds must also be in the
next part's list, or it is gone.  The record itself is gCourtRecord
(0x030028C0): evidenceList at +0x18 (32 bytes), profileList at +0x38 (32 bytes),
counts at +0x10 / +0x11, 0xFF = empty slot.

9.5  Verdict
------------
[44 1] guilty / [44 0] not guilty starts the verdict (process 9); [4A] waits for
its animation.


================================================================================
10. Investigations
================================================================================

The four investigation segments of the game share one engine.  The data for a
segment is loaded when it starts (InvestigationSegmentSetup_*), the room data
every time you enter a room (InvestigationRoomSetup_*).  Those functions are
code, not tables: who stands in a room, which event runs when you enter it,
which examine areas are active - all are decided by C code testing script
flags.  To change them you patch that code (or edit it in the decompilation).
Per part they are found through:
    gInvestigationSegmentSetupFunctions  0x0811201C
    gInvestigationRoomSetupFunctions     0x08112074
    gInvestigationRoomUpdateFunctions    0x081120CC
(22 pointers each; the trial parts point to an empty function.)

10.1  Rooms
-----------
Room ids are the same in the whole game (appendix F).  gMain.roomData
(0x030038D0, 26 rooms x 5 bytes) is copied from the segment's gRoomData_* table:
    +0 u8  background of the room
    +1 u8  Move destination 1 (room id, 0xFF = none)
    +2..+4 Move destinations 2-4
[32 room bg] and [33 room a b c d] change them, [34 room] goes to a room.  The
Move menu shows the picture gGfxLocationChoices + room id * 0x800.

10.2  Examine
-------------
gExaminationData (0x03003C90, 24 entries of 20 bytes, 0xFF-filled) is set by the
room setup code from gExaminationData_* tables:
    +0 u16  section to run
    +2 u8   type: 0xFE = "this animation on screen" (the next byte is the
            animation id), 0xFF = end of the list, else an area
    +3 u8   animation id (type 0xFE)
    +4      four corners (x, y as u16 pairs) of the area, in background pixels
GetExaminedAreaSection (0x08011408) checks the cursor against them
(after a few cases hard-coded for particular rooms); nothing hit = std section
0x1D ("nothing here").

10.3  Talk
----------
gTalkData (0x03002920, 32 entries of 20 bytes) is copied from gTalkData_*:
    +0 u8      room id
    +1 u8      person id
    +3 u8      enabled (a set of topics can be switched with [37])
    +4 u8[4]   topic pictures (gGfxTalkChoices index)
    +8 u8[4]   talk-end flag number of each topic (set 2: "heard")
    +12 u16[4] section of each topic
A room id of 0xFF ends the list.  Talk offers the topics of the entries whose
room is the current room, whose person is the one on screen and that are
enabled (1).

10.4  Present (in an investigation)
-----------------------------------
gInvestigationPresentData (0x08111FC4): per part, 10-byte
entries grouped by room:
    +0 u8   room id
    +1 u8   room sequence ([51]; 0xFF = any)
    +2 u8   evidence/profile id (0xFF = anything)
    +3 u8   person id (who must be on screen)
    +4 u8   1 = profile, 0 = evidence (0xFF ends the list)
    +6 u16  section when it is the right thing
    +8 u16  section otherwise ("I don't know anything about that")
GetEvidenceCommentSection (0x08013274) looks it up.

10.5  "Point at the picture" questions
---------------------------------------
[3E id] then [3F]: the player moves a pointer and presses A.  gSpotSelectData
(0x08022D0C, 8 entries of 0x2C bytes): two 4-corner areas, the section
for each and a default section, and the box the pointer can move in.

10.6  Map markers
-----------------
The little arrows and dots on maps and photos: [39]-[3D], [4B].  The kinds are in
sMapMarkerSprites (0x08022CA0, 9 entries: graphics pointer, size, OAM
attributes); their tiles go to OBJ tile 192 and up.

Investigation parts and their data (decompilation names; note that the suffix of
the names is not always the script file's):

  idx  5 (2-4): setup 0x08004C90, rooms 0x0801D6DC, talk 0x0801D470, present 0x0801CFF0
  idx  8 (3-1): setup 0x08005310, rooms 0x0801E220, talk 0x0801E018, present 0x0801DC84
  idx 11 (3-4): setup 0x08005A30, rooms 0x0801F1EC, talk 0x0801EFE4, present 0x0801EB80
  idx 14 (4-1): setup 0x08005FC0, rooms 0x0801FF70, talk 0x0801FE30, present 0x0801FC98
  idx 15 (4-2): setup 0x080062D4, rooms 0x08020954, talk 0x080206FC, present 0x0802039C

================================================================================
11. Psyche-Locks
================================================================================

Psyche-Locks are set up by the script.  gMain.psycheLockData (0x03003954) holds 4
lock sets of 40 bytes:
    +0x00 u32  enabled
    +0x04 u16  room id            +0x06 u16  person id
    +0x08 u8   locks left         +0x09 u8   locks in total
    +0x0A u16  start section      +0x0C u16  Stop (cancel) section
    +0x0E u16  right-evidence section (current)
    +0x10 u16  wrong-evidence section
    +0x12 u16  out-of-health section
    +0x14 u16  song after Stop    +0x16 u16  song after the last lock
    +0x18 u32  number of evidence that work
    +0x1C u8[4]  evidence ids     +0x20 u16[4] their sections
[4F] fills most of it, [60]/[61] the evidence, [66] the songs; [57] shows the
chains, [64] breaks a lock, [62]/[63] put the screen back, [71] ends it.
Talk topics behind a lock: [59 i]/[5A i] add/remove topic i of the segment's
gPsycheLockedTalkSections_* list (loaded to 0x03003B70).
The chains and locks are drawn by psyche_lock.c (state in gPsycheLock,
0x03006050); a lock screen is "background 0x7F" (gMain.currentDisplayBG = 0x7F,
there is no table entry for it).


================================================================================
12. Evidence and profiles
================================================================================

gEvidenceProfileData (0x08022F38): 156 entries of 8 bytes.  Evidence
and profiles share the same id numbers; whether an id is in the evidence or the
profile list is decided by the code that adds it ([17] bit 0x8000).
    +0 u32  pointer to the name + description picture: LZ77, unpacks to 160 4bpp
            tiles (0x1400 bytes) that go to OBJ VRAM 0x06013C00
    +4 u16  picture number in gGfxEvidenceProfilePictures
    +6 u16  Check screen (0 = none, else see below)
gGfxEvidenceProfilePictures (0x08177E28): 0x820 bytes per
picture: a 16-colour palette (0x20 bytes), then 64x64 px 4bpp (64 tiles).
LoadEvidenceGraphics (0x08012DDC) loads both.
The Check screen number picks a background (court_record.c):
    1 -> 0x15, 2 -> 0x16, 3 -> 0x2B, 4 -> 0x2A, 5 -> 0x30, 6 -> 0x31, 7 ->
    0x32, 8 -> 0x27, 9 -> 0x4C, 10 -> 0x4B, 11 -> 0x48, 12 -> 0x49, 13 ->
    0x53, 14 -> 0x47, 15 -> 0x47, 16 -> 0x47, 17 -> 0x65, 18 -> 0x64, 19 ->
    0x76, 20 -> 0x66, 21 -> 0x67
    (8 is a three-page newspaper: backgrounds 0x27, 0x28, 0x29.)
Script codes: [17] add, [18] remove, [19] replace, [13]/[14] show/hide the
evidence plate next to the box.  The full id list is appendix E.


================================================================================
13. Backgrounds
================================================================================

gBackgroundTable (0x0801ADC8): 127 entries of 8 bytes (ids 0x00-0x7E):
    +0 u32  pointer to the background data
    +4 u32  flags:
        bits 0-3  size: 0 = 240x160, 1 = 480x160, 2 = 360x160, 4 = 240x320,
                  8 = 240x240
        0x10 / 0x20 / 0x40 / 0x80  scroll direction (the decompilation's names:
                  HSCROLL_RIGHT, HSCROLL_LEFT, VSCROLL_TOP, VSCROLL_DOWN)
        0x100     mirrored left-right    0x200  mirrored top-bottom (unused)
        0x01000000  speed-line mode (background 0x10)
        0x80000000  4bpp, 16 colours (else 8bpp, 256 colours)
The data: ten u32 offsets (from the start of the data), the palette (0x20 bytes
for 4bpp, 0x200 for 8bpp; an 8bpp background only gets colours 32-255, 0-31
belong to the menus), then ten LZ77-packed stripes, each 16 px (2 tile rows) of
the picture, tiles row by row (a 240-wide 8bpp stripe is 60 tiles = 0xF00
bytes).  The first offset is 0x28 and points at the palette; the first stripe
follows the palette.  The game unpacks one stripe per frame (gMain.currentBgStripe)
- that is why a background change takes about 10 frames.

Special ids in the script: 0x80 = no picture (black), 0x7F = the Psyche-Lock
screen (display only), and bit 0x8000 = start the scroll from the other end.
0x0E, 0x0F and 0x14 are the bust-ups [46] uses; they have another format
(palette, a 30x20 map, then the tiles) and are not shown with [1B].
CopyBGDataToVram (0x080029B8) and DecompressBackgroundIntoBuffer
(0x08002820) do the work; UpdateBackgroundScroll the
scrolling ([1D], [4C]).
The list of backgrounds is appendix D.


================================================================================
14. People and animations
================================================================================

14.1  People
------------
gPersonAnimData (0x08023420): 46 entries of 12 bytes (person ids 0-45):
    +0 u32  graphics (it starts with a u32 palette count and the palettes)
    +4 u32  frame data (the poses)
    +8 u16  number of sprites
[1E person talk idle] shows a person.  "talk" and "idle" are byte offsets into
the person's frame data; each offset is the start of a pose (an animation).
The engine switches the speaker between the two on its own: talking while
letters appear, idle at the end of a box and during [4E] pauses.
A pose starts with an 8-byte header, then frames of 8 bytes:
    +0 u16  offset (from the pose start) of the frame's sprite list
    +2 u8   duration in frames; 0xFF = loop back, 0xFE = stop on this frame,
            0xFD = remove the animation
    +3 u8   flags: 0x2 play the sound in +4, 0x4 do the action in +5
    +4 u8   sound      +5 u8  action
The person on screen is gAnimation[1] (0x03000844).  PlayPersonAnimation is at
0x08014688, SetAnimationFrameOffset (pose change) at
0x080141E0.  Appendix C lists the persons and every pose offset
the script uses for them.

14.2  Other animations
----------------------
gAnimationData (0x08023648): 152 entries of 20 bytes for [2F id 1/0]:
    +0 u32 graphics  +4 u32 VRAM address  +8 u32 frame data
    +12 s16 x  +14 s16 y  +16 u8 palette  +17 u8 sprites  +18 u8 priority
Known ids: 1 'Hold it!' (left), 2 / 3 'Objection!' (left / right),
4 'Take that!' (left), 34 / 35 the Witness Testimony / Cross Examination logos
(36-39 their left/right halves).  The rest are effects and objects of single
scenes.


================================================================================
15. Sound
================================================================================

The game uses Nintendo's MusicPlayer2000 (m4a) sound engine.
    gSongTable  0x0802E584  245 entries of 8 bytes: song header pointer,
                u16 music player (0 = music, 1-3 = sound effects), u16
    gMPlayTable 0x0802E554  the four music players
Script codes: [05 song frames] play/fade in, [22 0 frames] fade out, [23 0 on]
pause/resume, [47 volume frames] volume, [06 se<<8|1] sound effect, [06 se<<8|0]
stop it.  Song 255 with [05] brings back a paused or faded-out song.
The table mixes music and sound effects (the player number says which).  The
script's [05] uses songs between 1 and 31 and between 201 and 243; most sound
effects are 42 and up.  Some known ones: 42 cursor, 43 confirm, 44 cancel, 45/46 male /
female blip, 47 text advance, 48 typewriter, 49 menu open, 52 switch record
page, 55 'Take that!' (voice), 58 gavel, 71 'Hold it!' (voice), 81 'Objection!'
(voice), 83 cross-examination start, 86 game over, 102 courtroom cheers.
PlayBGM 0x08013998, FadeInBGM 0x08013B14, PlaySE 0x08013834.


================================================================================
16. Processes and the main loop
================================================================================

The game is a state machine: gMain.process[0] (0x030037B8) is the current
"process", process[1] its state, process[2]/[3] sub-states.  gGameProcesses
(0x08111E18) holds one function per process:
     0  0x0800A7A8  CapcomLogoProcess        CAPCOM logo
     1  0x0800A860  TitleScreenProcess       title screen
     2  0x0800AC44  GameOverScreenProcess    game over
     3  0x0800D544  CourtProcess             court
     4  0x0800EB38  InvestigationProcess     investigation
     5  0x0800DA0C  TestimonyProcess         testimony
     6  0x0800DCF4  QuestioningProcess       cross-examination (questioning)
     7  0x08011730  CourtRecordProcess       Court Record
     8  0x0801176C  EvidenceAddedProcess     "added to the Court Record"
     9  0x0800E1EC  VerdictProcess           verdict
    10  0x0800B2AC  SaveGameProcess          save
    11  0x0800BFD8  EpisodeClearedProcess    episode cleared / new episode
    12  0x0800C404  SelectEpisodeProcess     episode select
    13  0x0800C9A4  ContinueSaveProcess      continue (load)
    14  0x0800AFB8  ClearSaveProcess         erase all data
Each frame AgbMain (0x08000218) waits for VBlank, then (when no background is
being loaded) updates the background scroll and tile maps, copies sprites to
OAM, writes the display registers, runs the script (RunScriptContext,
0x0800750C), updates the text box and evidence plate, runs the current
process (DoGameProcess, 0x08000314), the animations, fades and effects,
and the sound.  The script runs before the process each frame.
Soft reset: hold exactly A+B+START+SELECT.  Holding A while the game boots goes
to the "erase all data" screen (process 14).


================================================================================
17. Save data
================================================================================

The save is a straight copy of gSaveDataBuffer (0x02000000, 0x2BBC bytes) to
SRAM 0x0E000000.  Layout (struct SaveData):
    +0x0000  version string, 0x30 bytes: "2002 CAPCOM GBA GYAKUTEN-SAIBAN2 07/15
             Ver 1.000-" (gSaveVersion, 0x08022F04)
    +0x0030  u32 checksum
    +0x0034  gMain
    +0x02F4  display registers     +0x0348  gScriptContext
    +0x0388  gCourtRecord          +0x03E0  court scroll
    +0x03F0  testimony state       +0x03F8  investigation state
    +0x0414  gExaminationData      +0x05F4  gTalkData
    +0x0874  psyche-locked topics  +0x089C  map markers
    +0x093C  OAM copy              +0x0D3C  gTextBoxCharacters
    +0x103C  BG0 / BG1 / BG2 maps (0x800 each)
    +0x283C  32 animation backups (28 bytes each)
Checksum (CalculateSaveChecksum, 0x0800AF3C): start at 0, add the
byte at +0x34, +0x38, +0x3C ... (one byte out of every four) up to the end, then
add 2343.  The game refuses a save whose version string or checksum is wrong.
If you change the layout of these structures (in the decompilation), change the
version string so old saves are not loaded into the new layout.
SaveGameData 0x0800AE84, LoadSaveData 0x0800AECC.


================================================================================
18. Tips and traps
================================================================================

* Test from a new game, not from an old save: the save holds RAM pointers into
  the script and copies of the room/talk tables.
* Every part starts from a clean state: script flags and game-state flags
  cleared, the Court Record replaced by the part's list (9.4), in a trial also
  the read flags and room sequences.  Test a part on its own from the episode
  menu, and also by playing into it from the part before.
* Keep every line at 16 letters or fewer and every box at 2 lines (3 with [6E]).
* The script reads on into the next section if you forget [0D].
* The arguments of a code are u16s even when they hold small numbers: a tool that
  writes bytes breaks the stream.
* A part can have at most 256 sections (0x80-0x17F): the read flags have 256
  bits and the game does not check, so ending a section 0x180 or higher sets
  bits in gMain.roomData, right after the read flags.
* The engine finds section S at table index S - 0x80 and does not care whether
  that entry is a section or a jump label.  To add a section without disturbing
  anything, append its offset at the very end of the table (after the jump
  labels); its number is 0x80 + its index.  Inserting it before the labels
  moves them, and every [35]/[36] that uses a label must then be fixed.
* The game reloads the part from ROM on every [67], room changes in some rooms,
  and after loading a save: RAM-only edits do not survive that.
* The investigation room logic, Examine special cases and some events are C
  code (sections 10 and 16): the script alone cannot change who stands in a room.
* Graphics with text (section 6.5) need a graphics editor and LZ77.
* Free ROM: 0x08112A6C-0x0812FFFF and 0x087FC548-0x087FFFFF, or expand the ROM.
* Free RAM: see 7.1.  The game's IWRAM variables end at 0x030064B0 (the last one
  is gFlowerPetals); the stacks start at 0x03007F00 and 0x03007F80 (interrupts)
  and grow down.
* The decompilation is the best documentation: when these notes say "the code
  does X", the C source shows exactly how.
